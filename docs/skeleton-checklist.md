# Skeleton checklist

Recommendations for the `00-skeleton` spec, drawn from what production open-source databases and SaaS applications tell their agents and from practitioners who build with agents daily. Each item is a recommendation, not a rule. The `/interview-me-engineering 00-skeleton` session walks this list for the chosen stack, decides adopt, adapt or skip per item, and records the decision with a one-line reason in the spec. Implementation is stack and project specific.

Evidence and quotes: `research/2026-10-12-verifiable-foundations.md` in the local-setup repo.

## What production stacks set up

| Layer | What they do | Who |
| --- | --- | --- |
| Services | Postgres (and Redis, Mailpit) in docker compose with a `pg_isready` healthcheck; app container `depends_on: service_healthy`; the app itself has a health endpoint used as the compose healthcheck | FastAPI template, Twenty (`setup-dev-env.sh`), Coolify |
| Isolation | One compose stack per worktree or branch: Saleor's `.worktree-container/compose.sh`, Coolify names containers after the branch, Windmill gives each worktree its own database and ports from `.env.local`, Payload's fixture resets and seeds per test | Saleor, Coolify, Windmill, Payload |
| Bootstrap | One script: migrate then seed. FastAPI template's `prestart.sh` is two lines, `alembic upgrade head` and `python app/initial_data.py` | FastAPI template, Strapi, Twenty |
| Types | Strict everywhere, enforced not advised. `mypy strict` plus `ty` in pre-commit; TS `no-explicit-any` as an error and a ratchet so warnings cannot grow; "Never use `as any`"; Zod or tRPC at every boundary; Prisma `select` never `include` | FastAPI template, Formbricks, cal.com, Documenso, Twenty |
| Tests | Single-file invocation is the documented default, full suite is the exception. Test-as-data where possible. Offline, fixtures, frozen time. "A good failing test before implementing is good practice." Coverage checked per test | Zulip, Saleor, Twenty, Outline, Rails, Cockroach |
| E2E | Deliberately scarce. Formbricks: "An E2E test is paid on every PR, by everyone, forever," with a table of which level each change gets. Coolify runs Pest browser tests in-process against sqlite `:memory:` and writes screenshots to files the agent reads | Formbricks, Coolify, Strapi |
| Agent access to runtime | Laravel Boost ships MCP tools for exactly this: `database-query`, `database-schema`, `browser-logs`, `last-error`, `read-log-entries`. Twenty ships a read-only Postgres MCP. Steinberger: `psql` plus one example of loading env | Boost, Twenty, Steinberger |
| Gates | Pre-commit with ruff, mypy, biome; `make reviewable-api`; `pnpm check` as the one validation command; "smallest check that proves the change" during work, full set before push; human approval before any push | FastAPI template, Infisical, Ghost, Unkey, Grafana |
| Scope | PRs under 500 lines and 10 files; ask before schema changes, new dependencies, deleting files; "Do not run `npm run build` to verify changes" because it takes two minutes, use `tsc --noEmit` | cal.com, Documenso |
| Memory | Boost's `.ai/rules` with path globs and a `record-rule` tool; Infisical "update CLAUDE.md when you make significant changes"; Zulip's `/self-review` checklist skill | Boost, Infisical, Zulip |

Rows Services through Gates are adopted by default below. Scope and Memory are kept for reference, not adopted.

## Adopted by default

**1. Database and services in docker compose, with health checks.** `compose.yml` is the source of truth for Postgres and whatever else the app needs (Redis, Mailpit, MinIO). Every service has a `healthcheck`; the app `depends_on` them with `condition: service_healthy`. The app exposes a health endpoint that reports its dependencies and compose uses it as the app's own healthcheck. Day-to-day the services run in compose and the app runs however the framework runs it (`uv run fastapi dev`, `php artisan serve`, `yarn start`); the full stack in compose is for parity checks and deploy.
Sources: [FastAPI template compose.yml](https://github.com/fastapi/full-stack-fastapi-template/blob/master/compose.yml) and [development.md](https://github.com/fastapi/full-stack-fastapi-template/blob/master/development.md) (`docker compose up -d db mailpit`), [Twenty `setup-dev-env.sh`](https://github.com/twentyhq/twenty/blob/main/CLAUDE.md) (Postgres and Redis containers plus DB init), [Coolify](https://github.com/coollabsio/coolify/blob/v4.x/AGENTS.md) (compose with postgres, redis, vite, mailpit, minio, testing-host), [Laravel Sail](https://github.com/laravel/boost/blob/main/.ai/sail/core.blade.php), [OpenAI harness engineering](https://openai.com/index/harness-engineering/).

**2. One compose stack per worktree.** Isolation comes from compose itself: a compose project name and port offsets derived from the worktree directory, so two worktrees never share a database, a volume or a port. The repos do this with a thin wrapper around compose, not a custom runtime: Saleor's `.worktree-container/compose.sh` targets the current worktree's stack (`compose.sh up -d`, `compose.sh exec saleor pytest ...`); Coolify's `scripts/dev` starts "one dev instance per git branch (containers, volumes, VMs named after the branch)" from `docker-compose.dev-multi.yml`; Windmill writes the derived `DATABASE_URL`, ports and database name into `.env.local` and tells the agent to read that file rather than reconstruct the name. Starting the stack twice must be harmless.
Sources: [Saleor "Running in a git worktree"](https://github.com/saleor/saleor/blob/main/AGENTS.md), [Coolify "Development Environment"](https://github.com/coollabsio/coolify/blob/v4.x/AGENTS.md), [Windmill "Per-worktree ports and database"](https://github.com/windmill-labs/windmill/blob/main/AGENTS.md), [Ronacher on isolating shared state](https://lucumr.pocoo.org/2025/6/12/agentic-coding/), [OpenAI "bootable per git worktree"](https://openai.com/index/harness-engineering/).

**3. Bootstrap and smoke, using the framework's own commands.** Bootstrap is migrate then seed, as one script the agent runs after the stack is up: the FastAPI template's `prestart.sh` is `alembic upgrade head` then `python app/initial_data.py`; Laravel's is `php artisan migrate --seed`; Twenty's is `nx database:reset`. Seed data includes the known edge cases. Smoke is the health endpoint plus one real route via `curl`, exiting non-zero on failure; Anthropic's harness post calls the same thing `init.sh` and has the agent run it at the start of every session.
Sources: [FastAPI `prestart.sh`](https://github.com/fastapi/full-stack-fastapi-template/blob/master/backend/scripts/prestart.sh), [Twenty commands](https://github.com/twentyhq/twenty/blob/main/CLAUDE.md), [Anthropic long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [Willison, agentic manual testing](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing), [Hashimoto on simulation data](https://mitchellh.com/writing/non-trivial-vibing).

**4. Strict types, enforced not advised.** Python: `mypy --strict` plus `ty` in pre-commit, Pydantic at every boundary. TypeScript: `strict`, `no-explicit-any` as an error, Zod or tRPC at boundaries. PHP: `declare(strict_types=1)`, PHPStan at the project's level, typed request validation. Types regenerate across the wire where a client exists.
Sources: [FastAPI `pyproject.toml`](https://github.com/fastapi/full-stack-fastapi-template/blob/master/backend/pyproject.toml), [FastAPI pre-commit](https://github.com/fastapi/full-stack-fastapi-template/blob/master/.pre-commit-config.yaml), [Formbricks](https://github.com/formbricks/formbricks/blob/main/AGENTS.md), [cal.com](https://github.com/calcom/cal.com/blob/main/AGENTS.md), [Documenso](https://github.com/documenso/documenso/blob/main/AGENTS.md).

**5. Tests: targeted by default, offline, precise.** The documented way to run tests is the framework's single-test invocation (`pytest path::test`, `php artisan test --filter=name`, `npx jest path`), run inside the worktree's compose stack where the database lives (Saleor: `compose.sh exec saleor pytest --reuse-db path`); the full suite is the exception. Tests run offline with fixtures and frozen time. One real test exists before any feature. Assert exact values and state changes, never bounds or mere absence. Tests are data where the domain allows it (request plus expected response fixtures).
Sources: [Zulip testing rules](https://github.com/zulip/zulip/blob/main/.claude/rules/testing.md), [Saleor "Assert precisely"](https://github.com/saleor/saleor/blob/main/AGENTS.md), [Laravel Boost Pest guideline](https://github.com/laravel/boost/blob/main/.ai/pest/core.blade.php), [Rails AGENTS.md](https://github.com/rails/rails/blob/main/AGENTS.md), [Turso testing guide](https://github.com/tursodatabase/turso/blob/main/docs/agent-guides/testing.md), [DuckDB sqllogictest](https://github.com/duckdb/duckdb/blob/main/AGENTS.md), [Pocock tdd](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/SKILL.md), [Willison red/green](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd).

**6. End-to-end: one happy path per feature area.** Browser or HTTP driven, run on every PR; logic is tested at the unit level, not through the browser. Screenshots or response captures written to files the agent can read back.
Sources: [Formbricks testing guidelines](https://github.com/formbricks/formbricks/blob/main/AGENTS.md), [Coolify browser tests](https://github.com/coollabsio/coolify/blob/v4.x/AGENTS.md), [Anthropic long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents).

**7. Agent access to the running system.** The agent can query the database, read application and browser logs, and hit any endpoint without a human: `psql` with one env-loading example or a read-only DB tool, a dev API key for `curl`, log files in `tmp/` inside the repo with unique names per run, browser via Chrome tooling. Laravel: Boost's MCP tools cover database, schema, logs and browser logs.
Sources: [Laravel Boost MCP tools](https://laravel.com/docs/boost#available-mcp-tools), [Twenty read-only Postgres MCP](https://github.com/twentyhq/twenty/blob/main/CLAUDE.md), [Steinberger, workflow](https://steipete.me/posts/2025/optimal-ai-development-workflow), [Steinberger, Just Talk To It](https://steipete.me/posts/just-talk-to-it), [ClickHouse log redirection](https://github.com/ClickHouse/ClickHouse/blob/master/.claude/CLAUDE.md), [Osmani, workflow 2026](https://addyosmani.com/blog/ai-coding-workflow/).

**8. Logging the agent will not add on its own.** One logger, structured fields, to a file and the terminal, one "ready" line on startup, no secrets, and a test that asserts no secrets appear in log lines. Dev-mode emails and webhooks printed to stdout.
Sources: [Ouatiti et al., agents under-log](https://arxiv.org/abs/2604.09409), [Milvus logging rule](https://github.com/milvus-io/milvus/blob/master/CLAUDE.md), [TiDB no-secrets rule](https://github.com/pingcap/tidb/blob/master/AGENTS.md), [Ronacher](https://lucumr.pocoo.org/2025/6/12/agentic-coding/), [Vaughan enforcement](https://codex.danielvaughan.com/2026/05/01/agent-logging-gap-codex-cli-observability-enforcement-hooks/).

**9. Gates: pre-commit plus one validation command.** Pre-commit runs format, lint, typecheck, and a grep for skipped tests. One command, native to the stack (`pre-commit run --all-files`, `pnpm check`, `composer test`), runs the full Ready set before a commit is considered done. During work, the smallest check that proves the change.
Sources: [FastAPI pre-commit](https://github.com/fastapi/full-stack-fastapi-template/blob/master/.pre-commit-config.yaml), [Ghost `pnpm check`](https://github.com/TryGhost/Ghost/blob/main/AGENTS.md), [Infisical `make reviewable-api`](https://github.com/Infisical/infisical/blob/main/CLAUDE.md), [Unkey verification](https://github.com/unkeyed/unkey/blob/main/AGENTS.md), [TiDB verify profiles](https://github.com/pingcap/tidb/blob/master/.agents/skills/tidb-verify-profile/SKILL.md), [Osmani, harness engineering](https://addyosmani.com/blog/agent-harness-engineering/), [Pocock setup-pre-commit](https://github.com/mattpocock/skills/blob/main/skills/misc/setup-pre-commit/SKILL.md).

**10. Fail loud.** No fallback defaults that hide errors, no `sleep` to fix races, no swallowed exceptions, errors carry context. Written into `CLAUDE.md` Mistakes at skeleton time so the agent reads it from the first feature.
Sources: [ClickHouse](https://github.com/ClickHouse/ClickHouse/blob/master/.claude/CLAUDE.md), [Turso core principles](https://github.com/tursodatabase/turso/blob/main/AGENTS.md), [SurrealDB](https://github.com/surrealdb/surrealdb/blob/main/CLAUDE.md), [Vitess](https://github.com/vitessio/vitess/blob/main/CLAUDE.md).

## Optional, decide per project

**11. Module boundary lint.** Deep modules with a small public surface, enforced by a dependency lint that is proven to fail once before it is trusted. TypeScript: dependency-cruiser. Python: import-linter. Laravel: Deptrac. Most useful once the codebase has more than a handful of modules.
Sources: [Pocock setup-ts-deep-modules](https://github.com/mattpocock/skills/blob/main/skills/in-progress/setup-ts-deep-modules/SKILL.md), [Pocock, codebase not ready for AI](https://www.youtube.com/watch?v=uC44zFz7JSM), [OpenAI layer linters](https://openai.com/index/harness-engineering/).

**12. Review standards file.** A `coding-standards.md` read by `/code-review`, not by the implementing session.
Sources: [Pocock, Fixing the PR Bottleneck](https://www.youtube.com/watch?v=LlgiOCmFG_w), [Pocock code-review skill](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md), [Claude Code Review `REVIEW.md`](https://code.claude.com/docs/en/code-review).

## Not adopted, kept for reference

**Scope limits** (PR size caps, ask before schema changes and new dependencies). Common in team repos; the owner of this template is a solo developer who reviews by commit and has not adopted them. Sources: [cal.com](https://github.com/calcom/cal.com/blob/main/AGENTS.md), [Documenso](https://github.com/documenso/documenso/blob/main/AGENTS.md).

**Memory mechanisms beyond `CLAUDE.md` Mistakes** (path-scoped rule files, rule-recording tools, convention inference). The approach is not settled yet. Sources: [Laravel Boost project rules](https://laravel.com/docs/boost#project-rules), [Infisical](https://github.com/Infisical/infisical/blob/main/CLAUDE.md), [Zulip self-review](https://github.com/zulip/zulip/blob/main/.claude/skills/self-review/SKILL.md).

## Stack hints

**Python, data and AI pipelines (scrapers, ETL).** Services are often just Postgres and object storage; item 6 may be a CLI run over a fixture directory rather than a browser path; item 3's seed is a small captured dataset including malformed records; Thariq's pattern applies: a synthetic data set of "all the things that have broken in the past" run through the CLI. Start from the FastAPI template's `pyproject.toml` and pre-commit for items 4 and 9 even when there is no web app.

**Laravel, SaaS website.** Install Boost first: `composer require laravel/boost --dev && php artisan boost:install`. It covers item 7 (MCP tools) and much of items 5 and 9 (Pest guidelines, `enforce-tests`). Boost's own position on verification scripts ("Do not create verification scripts or tinker when tests cover that functionality") conflicts with the end-to-end step in `/implement`; keep the end-to-end step for the spec's acceptance and let Boost's rule govern ad hoc checks. Pest browser plugin for item 6, Pint plus PHPStan for item 4, Deptrac for item 11.
